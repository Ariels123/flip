# Vibe Scorecard - Quality Evaluation System Design

**Version:** 1.0
**Created:** 2026-01-01
**Status:** Design Complete
**Depends on:** FLIP2 v1.0 production deployment

---

## Overview

The Vibe Scorecard is a quality evaluation system that uses LLMs to assess task outputs across four critical dimensions. It enables:

- **Automated Quality Assurance** - Evaluate work without human review delay
- **Performance Tracking** - Identify which agents excel at which tasks
- **Continuous Improvement** - Auto-retry low-quality outputs with feedback
- **Trend Analysis** - Monitor quality improvements over time

---

## Design Goals

1. ✅ Simple, explainable evaluation criteria
2. ✅ Quantifiable scores (0-10 scale)
3. ✅ Actionable feedback for improvement
4. ✅ Lightweight for high-volume evaluation
5. ✅ Supports retry loops with history tracking

## Scoring Dimensions

### 1. Correctness (0-10)

**What:** Does the output work correctly and meet requirements?

**Evaluation Criteria:**
- 10: Perfectly correct, all requirements met
- 8-9: Works correctly with minor issues
- 6-7: Works mostly correct with notable gaps
- 4-5: Works but has significant issues
- 2-3: Mostly broken or incorrect
- 0-1: Completely broken or non-functional

**Example Feedback:**
> "The function correctly handles the main use case but fails to validate empty inputs. Missing null checks on database queries."

### 2. Efficiency (0-10)

**What:** Is the solution performant and optimized?

**Evaluation Criteria:**
- 10: Optimal time/space complexity
- 8-9: Good performance, minor optimizations possible
- 6-7: Acceptable performance, some improvements possible
- 4-5: Noticeable performance issues
- 2-3: Significant inefficiencies (N² algorithms, etc.)
- 0-1: Extremely inefficient or causes hangs/crashes

**Example Feedback:**
> "The algorithm uses an O(n²) nested loop where O(n log n) sorting would be more efficient. Consider using a hash map instead of repeated searches."

### 3. Maintainability (0-10)

**What:** Is the code clean, readable, and maintainable?

**Evaluation Criteria:**
- 10: Excellent documentation, clear structure, easy to modify
- 8-9: Good code quality, mostly clear intent
- 6-7: Adequate quality, could benefit from more comments
- 4-5: Difficult to understand, poor structure
- 2-3: Confusing code, inadequate documentation
- 0-1: Unreadable spaghetti code

**Example Feedback:**
> "Variable names are cryptic (x, y, z instead of width, height, depth). Missing docstrings for public functions. Complex conditional could be split into smaller functions."

### 4. Security (0-10)

**What:** Does the solution have security vulnerabilities?

**Evaluation Criteria:**
- 10: No apparent security issues
- 8-9: Minor potential issues
- 6-7: Has some security concerns
- 4-5: Multiple security issues
- 2-3: Critical vulnerabilities
- 0-1: Severe vulnerabilities, no error handling

**Example Feedback:**
> "SQL injection vulnerability: User input not parameterized. Missing CORS headers. No authentication on admin endpoints."

---

## Scoring Formula

### Overall Score Calculation

```
overall_score = (correctness + efficiency + maintainability + security) / 4
```

**Range:** 0.0 - 10.0

**Example:**
```
Correctness:     8.5
Efficiency:      7.0
Maintainability: 8.0
Security:        8.5
─────────────────────
Overall Score:   8.0  ← (8.5 + 7.0 + 8.0 + 8.5) / 4
```

## Pass/Fail Determination

### Status Logic

```go
func (v *VibeScoreCard) DetermineStatus() Status {
    threshold := v.QualityThreshold
    if threshold == 0 {
        threshold = 6.0  // Default
    }

    if v.OverallScore >= threshold {
        return StatusPass
    }
    return StatusFail
}
```

### Status Meanings

| Status | Meaning | Action |
|--------|---------|--------|
| `pass` | overall_score >= threshold | Accept result, move forward |
| `fail` | overall_score < threshold | Reject result, queue for retry |
| `needs_review` | Manual determination | Human review required |

### Default Threshold

- **Quality Threshold:** 6.0/10
- **Rationale:** Allows improvement room while filtering clearly inadequate work

## Retry Loop Integration

### Retry Workflow

```
1. Agent completes task → TaskResult created
2. Vibe Scorecard evaluates (score: 4.0/10)
3. Score < threshold (6.0)
4. System queues retry with feedback:
   "Previous attempt scored 4.0/10 because:
    - Security: Missing input validation
    - Efficiency: O(n²) algorithm
    Please address these issues in your next attempt"
5. Agent retries with guidance
6. New Vibe Scorecard created (score: 8.5/10)
7. Score >= threshold: Accept result
```

### Retry Tracking

Each retry scorecard includes:

- `retry_count`: Number of retries (0 = first attempt)
- `previous_score_id`: Links to previous evaluation
- Full history preserved in database

**Query Example:**
```sql
-- Find all attempts for a task
SELECT * FROM vibescore
WHERE task_id = 'task_123'
ORDER BY evaluated_at ASC
```

## Database Queries

### Find Latest Evaluation for Task

```sql
SELECT * FROM vibescore
WHERE task_id = ?
ORDER BY evaluated_at DESC
LIMIT 1
```

### Find All Retries for Task

```sql
SELECT * FROM vibescore
WHERE task_id = ?
ORDER BY evaluated_at ASC
```

### Agent Performance (Last 30 Days)

```sql
SELECT
  evaluator,
  COUNT(*) as evaluations,
  AVG(overall_score) as avg_score,
  COUNT(CASE WHEN status = 'pass' THEN 1 END) as pass_count,
  COUNT(CASE WHEN status = 'fail' THEN 1 END) as fail_count
FROM vibescore
WHERE evaluated_at >= datetime('now', '-30 days')
GROUP BY evaluator
```

### Quality Trends

```sql
SELECT
  date(evaluated_at) as date,
  AVG(overall_score) as avg_score,
  COUNT(CASE WHEN status = 'pass' THEN 1 END) as passes,
  COUNT(CASE WHEN status = 'fail' THEN 1 END) as failures
FROM vibescore
WHERE evaluated_at >= ?
GROUP BY date(evaluated_at)
ORDER BY date ASC
```

## Threshold Tuning

### Recommended Default: 6.0/10

| Threshold | Implication | Use Case |
|-----------|-------------|----------|
| 4.0 | Very permissive, accepts flawed work | Learning/experimentation |
| 5.0 | Permissive, focuses on correctness | MVP/prototype |
| **6.0** | Balanced, good quality baseline | Standard (recommended) |
| 7.0 | Strict, high-quality requirement | Production critical |
| 8.0 | Very strict, research-grade | Scientific work |

### Dynamic Thresholds (Future)

```go
// Adjust based on task priority
func calculateThreshold(task *Task) float64 {
    switch task.Priority {
    case "critical":
        return 8.0
    case "high":
        return 7.0
    case "normal":
        return 6.0
    case "low":
        return 5.0
    default:
        return 6.0
    }
}
```

## Performance Notes

### Index Strategy

All queries use indexed columns:
- `task_id` → Fast lookups for retries
- `evaluator` → Agent performance stats
- `evaluated_at` → Time-range queries
- `overall_score` → Sorting/filtering
- `task_id + evaluated_at` → Composite for latest eval

### Expected Query Performance

- **Lookup by task_id:** < 5ms (indexed)
- **Agent stats:** < 50ms (GROUP BY, indexed)
- **Trend analysis:** < 200ms (large date ranges)
